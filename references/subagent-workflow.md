# 子代理字幕组：岗位、派单与交接

本协议把字幕制作阶段落实为实际子代理任务。主代理是制片统筹，不轮流扮演所有员工；使用运行环境提供的子代理工具创建、派单和等待，不创建用户侧的新聊天，也不把 Python 子进程、API 调用或提示词中的角色名当作子代理。这里是调度约定，现有 Python 脚本不会自动创建代理或维护工单。

## 岗位及交付边界

按需要启用岗位，不为被跳过的阶段创建空任务。每个员工只承担本岗位；可在同岗位内复用处理后续批次。翻译、校对和编辑始终是不同实例，质检也不由该稿的编辑自验。默认继承父代理模型与推理配置，不硬编码型号。

| 岗位 | 输入与工作 | 交给主代理的产物 | 不得代行 |
| --- | --- | --- | --- |
| 素材员 `intake` | 本地原件或视频链接、主代理冻结的下载选择；按 media-intake.md 登记/下载，核对媒体、字幕轨、语言、时长与能力 | 已验收候选本地媒体、media-manifest.json、散列、可用轨道与路由建议 | 修改用户偏好、擅切下载后端/重提计费解析、擅用自动字幕或上传发布 |
| 转写员 `transcriber` | 已选后端、音轨或作者台词；VAD、ASR、词级对齐、疑点听校 | 原始后端结果、绝对时间映射、job ID、实际听校范围 | 用模型认同冒充听见原音；重复提交收费任务 |
| 视觉员 `vision` | 真实视频帧及对应时间；实际看图 | 符合视觉协议的响应、已看 frame ID、工具与不确定性 | 从 ASR 猜画面，或替换讲者原话 |
| 原文整理员 `preprocessor` | 原始转写/作者字幕及音画证据 | 保留源 ID 的原文候选、修正依据、source_checks、语义组映射；采用字符边界时附时间证据包 | 无证据改原话、按字数造时间 |
| 术语与记忆员 `terminologist` | 整理后原文、领域/地区、上下文与证据 | 全片逐 ID 发现记录、核验来源、词义/译名候选、章节与风格档案 | 把推测写成事实，私自更新冻结术语库 |
| 翻译员 `translator` | 冻结术语版原文、核心批次、只读上下文及风格档案 | 每个核心 ID 的 `draft` 响应 | 写 `target`、自校自审、创造新首选译名 |
| 校对员 `proofreader` | 完整初译阶段冻结后生成的本批原文、draft、证据 | `proofreading_status`、`suggestions`、`proofreading_note`；新源文疑点另附记录 | 替换 draft/target、将开放疑点判 PASS |
| 编辑员 `editor` | 校对阶段冻结后生成的本批原文、draft、建议及证据 | `target`、`review_note`、`review_status`、`issues`，按协议附解决证据 | 忽略建议直接盖章、靠流畅度消除疑点 |
| 制作员 `producer` | 编辑稿、timing_mode、真实词边界与显示要求 | timing-plan、排版/拆合候选及映射；采用字符边界时新建或更新时间证据包；验收后的版本可导出到本任务独占目录 | 固定轴任务改轴；改文/改轴后继承旧审定 |
| 质检员 `qa` | 冻结交付候选、原文、术语和全部审校记录 | 机器 QA、全片词义/译法一致性复核、抽查范围、例外与 verify-export 结果 | 直接改交付文件或把技术通过当语义无误 |

每位员工先读技能入口、本协议的岗位边界及工单列出的必读参考。主代理按任务传递参考的绝对路径及实际版本：素材员读 media-intake.md，首次选择由主代理和用户完成；素材/转写读对应媒体后端及作者字幕规则；视觉读 multimodal-context；原文整理读 review-evidence，语音疑点再读 audio-review；术语员读 terminology；翻译/校对/编辑读 data-and-tools、本地化、表达方式及项目适用的平台/游戏规则，修改已有译文另读 semantic-preservation；制作/质检读 workflow、data-and-tools 及适用的时间轴、保真、排版规则。正文和风格档案必须实际加载，散列不是提示词正文。

## 调度与依赖

1. 主代理确定任务范围、工作目录、可用工具和并发额度，建立工单与唯一写入目录。员工不得递归派生其他员工；需要新岗位、外部证据或返工时回报主代理统一安排。
2. 素材检查后，转写与真实帧分析可在输入已具备时并行。ASR-first 的视觉关联等待字幕区间。原文整理等待所需音画证据完成或明确降级；全片术语发现、核验、绑定和上下文档案冻结后才派翻译。
3. 默认采用阶段屏障：全片初译完成并 audit 后，生成校对批次；全片校对合并后，生成编辑批次；编辑完成后进入制作和质检。这样现有 `chunks/apply` 协议无需支持跨阶段抢跑。发现阻断问题先返工，不把未齐的批次宣称全片完成。
4. 同一阶段可将不重叠核心 ID 的批次并行派给多名同岗员工；前后文是只读。章节、术语和风格使用同一冻结版本。批间依赖强或槽位不足时，同岗员工按顺序做多个批次。并发数量以实际环境额度为上限，计入主代理及其他活跃代理；不假定所有岗位同时在线。
5. 员工完成后等待其真实结束，按环境支持的方式释放/回收资源再启动后续岗位；仅在工具确有此能力时调用，不虚构“关闭代理”接口。槽位暂满先排队或等待，不立即用主代理代替校对。无法继续创建时适用后文降级规则，不把翻译实例改名为校对实例。
6. 主代理串行验收响应、调用适用的 `apply/bind` 并另存新版本。源文整理、制作候选等无通用 apply 的产物，先核对差异、源 ID 映射、结构和失效范围，再以新版本纳入。员工不能直接写正式源稿、术语快照、其他岗位产物或共享 manifest。

在提供 `collaboration` 工具的环境，主代理可用 `spawn_agent` 创建岗位、`followup_task` 派发同岗位后续批次、`send_message` 传递补充信息、`wait_agent/list_agents` 等待与确认。校对与编辑优先创建空白上下文实例（如支持则 `fork_turns="none"`），只给工单和必要文件；不携带翻译员的自我评价或未落盘推理。没有上下文隔离选项时仍用不同实例，并记录继承上下文这一限制。派单时不指定模型覆盖，除非用户已要求。其他环境用其实际对应工具，不把这些工具名当作通用 API。

## 工单与响应

项目内采用 `jobs/<stage>/<batch-id>/<attempt-id>/`，每次派单/返工独占新目录。例如 `jobs/translate/b00001/a01/` 下保存主代理写的 `assignment.json`、员工写的 `result.json` 和 `handoff.json`。非批次任务可使用 `whole` 代替 batch-id。工单与交接记录是调度侧文件，不塞进脚本批次，也不改变 `schema_version=1` 或 `workflow=vidove-inspired-v1`。

主代理生成工单时填写实际值，不用示例摘要代替计算结果：

创建顺序：先完整写好工单，`agent_id` 暂为 null，状态为 queued；再创建员工并提供该工单路径。创建返回真实 ID 后，主代理将 ID 登记到独立的任务状态记录和 manifest，不在员工读取期间改写冻结工单。员工从自身运行时取得 ID 写入 handoff；无法取得则留 null，由主代理依据创建结果核对并补记到验收记录，不猜测。复用已知员工时工单可直接写真实 ID。工单、创建结果与验收记录通过 task_id/attempt 关联。

| 工单字段 | 内容 |
| --- | --- |
| `task_id / role / attempt / agent_id` | 唯一任务号、岗位、尝试号、已知真实代理标识；首次创建前允许 agent_id 为 null |
| `skill_root / project_root / output_dir` | 绝对路径；唯一允许员工写入的任务目录 |
| `inputs` | 每个冻结输入的绝对路径、SHA-256、用途；批次还记真实 batch_id/input_digest |
| `timing_evidence` | 涉及字符级拆分时必填：适用核心/邻条 ID、证据包绝对路径和 SHA-256；包及需读摘录同时列入 inputs，规范见 [字符级时间证据](character-timing-evidence.md) |
| `scope` | 核心 ID、只读相邻 ID、适用媒体区间；全片工作写明覆盖范围 |
| `required_reading / profiles` | 必读规则及本地化/术语/提示词文件路径与版本摘要 |
| `constraints` | 语言、地区、领域、timing_mode、交付格式、已有授权及能力限制 |
| `output_contract / acceptance` | 阶段 JSON 协议、允许字段、预期完整 ID、需交回的证据与检查 |

派单前核对核心及只读邻条的构轴方式；字符级拆分包括从旧项目继承的分段。将时间证据包和必要摘录列为默认输入，将 character-timing-evidence.md 列入必读，并在验收条件中要求核对边界计算。包尚待原文整理/制作岗位生成时，先列为该上游工单的交付物，验收后才供下游使用。校对、编辑、制作、质检等后续相关工单沿用同一冻结包；缺项由主代理先组织补齐，不能仅传 asr_words 或靠员工聊天追问。具体内容、缺失处理和版本绑定均按该参考执行。

给员工的派单提示可直接采用以下结构，填入实际工单路径和岗位职责：

> 你是本项目的【岗位】子代理，只负责工单中的工作。读取【assignment.json 的绝对路径】、技能入口和工单指定参考，再核验输入版本。只处理核心范围，邻条仅供理解。只在 output_dir 写入符合阶段协议的 result.json 和 handoff.json；不改源文件、共享 manifest 或其他员工目录，不创建子代理。发现缺证据、新术语、源文错误或过期输入时提交具体 ID、依据和返工请求。完成后报告工件路径、实际覆盖和未决项，等待主代理验收。

翻译、校对、编辑的 `result.json` 沿用 [data-and-tools.md](data-and-tools.md) 原有响应形状和 batch 摘要。其他岗位沿用相应参考中的协议。`handoff.json` 记录 task_id、role、agent_id、输入摘要、输出文件及 SHA-256、covered_ids/媒体范围、实际工具与证据来源、未决项、所需返工、下一步和 `outcome`（completed/blocked/needs_revision）。completed 只表示该员工完成工作，不等于字幕 reviewed 或已被主代理接受；完成一份 UNCLEAR 校对报告也可是 completed。

新 source_checks、源文修正和新术语建议用交接侧文件承载，不伪造为 proofread/apply 可写字段。主代理将有效疑点纳入新的源版本后，重新生成受影响批次；只写在聊天或 handoff 中的疑点不算进入正式证据协议。

## 验收、合并与返工

- 核验工单、实际代理身份、输入/输出文件可解析性、SHA-256、完整且唯一的核心 ID，以及本岗位允许字段；范围外内容拒收。主代理的核对不能只依赖员工自报的散列。脚本只检验它支持的字段，岗位边界仍须主代理验收。
- 字符级时间证据须覆盖工单中涉及的核心及只读邻条，绑定当前源文/parent_ids/显示起止，能从实际对齐记录和规则复算边界；验收同时核对 handoff 中实际读取的包及摘要、缺项和处理结论。上下游包版本须一致或有明确更新依据，不将缺失的构轴依据默认为已核验。
- 检查冻结输入文件本身未变，并使用原 batch_id/input_digest 应用响应。并行批次的结果在最新有效累计稿上逐批串行 apply，不从共同旧版本分别生成整片稿后互相覆盖；不用复制旧摘要强行接受陈旧响应。累计稿全文件散列因其他不重叠批次合并而变化是正常的，是否可应用还须通过脚本对核心条目、meta 和只读源文上下文的检查。
- 确认规定的保真、自然度、术语及证据检查已落实到具体文本；机器校验成功并不证明语义已审。观察能力逐员工确认：视觉员看过帧可作为下游的带出处证据，校对员不能因此声称自己也看过；音频同理。
- 新词或词义冲突退回术语员；疑似 ASR 错误退回转写/原文整理员；译文问题退回翻译或编辑岗位；阅读性/轴问题退回制作员。主代理验收上游修正后另存版本，再重建受影响下游。重新 bind 目前会保守清空全片 target 和审定，按脚本实际失效范围返工，不能只重做报错那一行。
- 仅增删或更新 source_checks 时，至少重建包含受影响核心/只读上下文的批次，并重做对应校对、编辑；术语快照能否保留须通过 validate_bound，专门证据流程要求重绑时仍须重绑。改变 source、时间、source_notes、音画线索或词义/译名时重新核查术语发现与绑定；一旦 bind 或全局 meta 改变，遵守实际全片失效范围。不能仅凭“文字没变”继承旧审定。
- 制作员仅提出语义改写、拆合和调轴候选；纳入新版本后按原规则重新关联证据、绑定术语和审校。质检员发现问题交回相应岗位修复，再校验最终导出的字幕。不得通过手改 SRT 绕过编辑记录或 verify-export。
- 格式错误可退给同岗员工以新 attempt 修复；证据不足不靠反复生成“解决”。同一问题修复后仍重复失败时定位输入、协议或能力原因，保留有效工件，记录 blocked/needs_revision 并继续不依赖它的工作，不无限派单。

## 进度、恢复与能力降级

manifest 仅由主代理写入。在现有阶段记录外添加调度信息：execution_mode、任务工单路径、role/agent_id、attempt、输入/输出摘要和任务状态。任务按 `queued → running → returned → accepted` 流转；失败记录 failed/blocked/stale 及原因。returned 不能计入阶段完成覆盖；只有验收、合并并记录正式版本后才 accepted。`needs_review` 是字幕编辑状态，与任务状态分开。没有执行的岗位记 skipped 和原因。

合并使用主代理维护的两份侧记录，不假定 apply 和 manifest 是一个事务：

1. apply/bind 或其他正式版本写入前，保存 `merge-intent.json`：task_id/attempt、阶段、父版本路径及 SHA-256、批次/响应摘要、计划输出的唯一版本路径和具体操作。该文件及下一步收据由主代理写入单独的 `merges/<task-id>/<attempt>/`，员工不能写入。
2. 输出成功且验证后保存 `merge-receipt.json`，引用 intent 摘要并记录实际输出路径、SHA-256、覆盖 ID 与验收结论；然后让 manifest 的 accepted 记录引用该收据。收据和意图不由现有脚本自动生成。
3. 重启时，收据完整且父版本、响应和输出摘要相符，才可补登记 manifest。仅有 intent 和输出而缺收据时，重新验证；可重放的 apply 阶段在新的恢复目录重放并比较结果，不能覆盖已有版本或再次应用到已合并稿。无法证明一致就保留待验收，另存新版本处理，不按文件名、时间戳或状态文本认定成功。

续做遵守 [checkpoint-recovery.md](checkpoint-recovery.md)。若代理尚可查询，先确认任务真实状态；无法确认旧员工是否仍在运行时不复用其目录，新任务使用新 attempt，并保证只接受一个与当前输入匹配的结果。代理已结束但工件尚未验收时先验收，不重复生成。代理内存或聊天记录不充当唯一检查点。旧任务缺少岗位记录时记 legacy/unknown，不补造历史代理 ID，不因采用新调度而重做已验证有效的成果。

工具不可用、禁止委派或确实无法分配新实例时，在 project/manifest 记录 `execution_mode=single-agent-fallback`（局部例外用 mixed）、原因、受影响岗位和实际执行人，并告知用户。普通任务可继续分阶段完成；若用户明确把独立子代理审校作为验收条件，则保留草稿及未完成队列，不以主代理自审冒充履约。不要因为批次短或图省事而降级。

某员工无图像、音频或联网能力时，主代理可将证据获取交给有实际能力的专岗；只有主代理具备能力时可记录为 mixed，由主代理真实获取证据后交回岗位继续处理。不存在可用能力则按原规则记 unavailable、proposed 或 UNCLEAR。把“已提取文件”“其他代理说看过”与自身实际审阅区分开，保留证据生产者和范围。分工不会增加工具权限，也不扩大云端发送、DeepSeek 或收费调用的授权范围；不向工单写入密钥，不向翻译链传递评测参考文本。
